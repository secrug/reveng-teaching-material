What reverse engineering is

A compiler turns source into machine code.
Reverse engineering goes the other way: from machine code to an understanding of what a program does.

Not to the source code. The source is usually not recoverable — and not because it's hidden.

Because it no longer exists anywhere in the file.

Inference, not decryption

Compilation is lossy. It discards information permanently — like converting a photo to greyscale.

You can guess what colour a grey pixel was. You are guessing, and no cleverness turns a guess into a measurement.

So RE is inference: reasoning from evidence to the most plausible explanation, under uncertainty.

Closer to reading an X-ray than decrypting a message. An X-ray is interpreted — and the interpretation is only as good as the reader's knowledge of anatomy.

The evidence is always complete. Every byte is there, nothing is hidden. What varies is how much of it you can read. This course builds the anatomy knowledge.

The compilation pipeline

One command, gcc hello.c -o hello, is actually four steps.


hello.c  ──cpp──▶  hello.i  ──cc1──▶  hello.s  ──as──▶  hello.o  ──ld──▶  hello

source            preprocessed        assembly         object           executable
                                                       (relocatable)     (linked)

Every arrow runs one way.

Run it yourself


gcc -E hello.c -o hello.i    # preprocess: 5 lines becomes ~800
gcc -S hello.c -o hello.s    # compile:    now it's assembly
gcc -c hello.s -o hello.o    # assemble:   now it's bytes
gcc    hello.o -o hello      # link:       now it runs

At each arrow, ask: what did we just lose?

Do this live. Scroll hello.i so they see 800 lines of stdio.h. The reaction is the point.

What each stage destroys

StageDestroys
cppcomments, macro names, include structure
cc1variable names, types, expression structure, some function boundaries, control structure
asnothing of interest — asm and machine code are two notations for the same thing
ldsource-file boundaries; symbol names if stripped

Why disassembly is reliable and decompilation is not: the assembler threw nothing away, the compiler threw nearly everything away.

The compiler's losses, concretely

  • Names. customer_balance becomes [rbp-0x18]
  • Types. The machine has no int, float, char*, struct account — only registers, addresses, and widths
  • Expression structure. (a+b)*c and equivalent temporaries compile identically
  • Function boundaries. Small functions get inlined and cease to exist
  • Control structure. for, while, and goto loops can produce the same jumps

A type is a fiction the compiler maintained during compilation, then discarded.

The central idea

Compilation is many-to-one


int f(int n) {
    int s = 0;
    for (int i = 1; i <= n; i++)
        s += i;
    return s;
}
    

int g(int n) {
    return n * (n + 1) / 2;
}

At -O0: clearly different. One has a loop.

At -O2: the compiler recognises the closed form. These can compile to byte-identical machine code.

Given only that machine code —
was the source f or g?

There is no answer.

Not "hard to find". Not "we need a better tool".

The information no longer exists.

Two different inputs produced the same output.
No function inverts a many-to-one mapping.

Three consequences

  1. A perfect decompiler is impossible. Not impractical — impossible, for information-theoretic reasons. Any tool claiming to recover source produces a plausible source, not the source.
  2. The same limit applies to any tool at all, including one that has read every program ever written. Better priors let you guess better. They do not recreate destroyed information.
  3. So the goal is not to recover the source. It's to build a model of the behaviour that is good enough for your purpose.

"Good enough for the purpose" is a judgement call. Judgement is the skill.

What survives

Compilation cannot destroy anything the machine needs in order to run.

SurvivesWhy it helps
Control flow structureLoops must still loop, branches still branch
String & numeric literalsMust be in memory to be used
Library / system callsMust be named for the linker to resolve
Data layout, offsetsThe machine needs exact addresses
SyscallsThe kernel boundary is fixed and numbered
Algorithmic shapeAES still contains the AES constants

The principle behind every technique in this course

Look for what the compiler
had no choice about.

Forward-reference lightly: argument registers reveal signatures (L4) because the ABI isn't optional. Address scaling reveals element size (L5) because the machine must compute the right address. Padding reveals struct layout (L5) because hardware requires alignment.

Magic numbers

Files announce their type with fixed bytes, almost always at offset 0.

BytesFormat
7f 45 4c 46ELF — Linux executables, objects, shared libs
4d 5aPE / MZ — Windows executables
89 50 4e 47PNG
1f 8bgzip
ca fe ba beJava class / Mach-O fat binary

7f 45 4c 46 is 0x7F then ASCII E L F — one non-printable byte so it's never mistaken for text, then a human-readable tag.

file is a heuristic

file matches signatures against a rule database. It does not read the filename, and it does not verify the whole file.

Two failure modes you'll meet today:

  • A file with one damaged magic byte reports as data — while remaining a perfectly well-formed PNG
  • A file can be constructed to match a format it isn't

file gives you a hypothesis.
xxd gives you evidence. Confirm.

Three seconds. It will save you hours.

The triage toolbox


file X            # what is it?  (a hypothesis — confirm it)
xxd X | head      # the actual bytes: magic number, structure
strings -n 8 X    # printable runs: errors, formats, paths, banners
nm -C X           # symbol names, if not stripped
readelf -h X      # header: architecture, type, entry point
readelf -d X      # dynamic: which libraries it needs
readelf -S X      # sections: .text, .rodata, .data, ...

Run these before any disassembly. Every time.

strings: the first technique

$ ./crackme01 password: hunter2 nope.

The program must compare your input against something. The simplest implementation stores that something as a string literal — which lives in .rodata, where strings reads it straight out.

Crude. Frequently the most productive thirty seconds you will spend on a binary.

Cold open lives here. Let them solve it — including with a model. Both are supposed to happen. Then hand out crackme01x.

… and its limit

Same program. The expected password is now XOR-encoded and decoded at startup.


static char secret[] = { 0x2a, 0x31, 0x2e, 0x2b, ... };  /* each byte ^ 0x5A */

for (int i = 0; i < len; i++)
    secret[i] ^= 0x5A;
$ strings crackme01x | grep -i pass password:

The password is gone. The bytes aren't printable, so they aren't printed.

Why that matters

The obfuscation isn't clever. It's trivial.

The point is that the technique which worked a moment ago told you nothing about why it worked — so it gives you nothing to fall back on when it stops.

It also failed silently. An empty result looks exactly like "there was nothing to find."

And the program still knows the password. It must — it compares your input successfully. The decoding loop is right there, doing the work for you.

The program always tells you.
The only question is whether you can read it.

Optimisation levels

LevelWhat you'll see
-O0Every variable gets a stack slot; explicit load/store for each access. Assembly maps closely to source. Friendly to read — and not what real software ships as.
-O2Production. Variables live in registers, loads/stores vanish. Small functions inlined away. Loops unrolled, rewritten, or replaced with closed-form arithmetic. Dead code removed. Computations reordered.
-OsOptimise for size: less inlining and unrolling, shorter encodings preferred.

Same source, very different binaries. A technique that works on -O0 examples may not transfer to -O2 code — which is why we use both.

Worked example · first contact

AURA-7

A firmware image from a synthetic embedded device. We'll take it apart across the whole course.

$ file aura-fw.bin aura-fw.bin: data

Correct, and useless. No signature matched. Firmware images generally have no standard format — the only software that reads them is the bootloader that shipped with the device.

What strings gives us

AURA-7 firmware v1.2 (c) 2019 Aura Systems /dev/ttyS0 AURA

Four pieces of text, one hypothesis: an embedded device that talks over a serial port and has a version number.

Now look at the bytes directly.

The header

$ xxd aura-fw.bin | head -1 00000000: 4155 5241 0100 0200 0020 0000 .... AURA.... ...

41 55 52 41 = AURA in ASCII. A magic number — just not one file knows about.

The device's own bootloader checks those four bytes to confirm it's been handed a valid image. Exactly as the kernel checks 7f 45 4c 46.

Decode the four bytes by hand at the board. It should look easy, because it is. First time they see bytes-to-meaning done manually.

Endianness

The bytes at offset 4 are 01 00 02 00. What version is that?

x86 is little-endian: multi-byte integers are stored least-significant byte first.

So the u16 at offset 4 isn't 0x0100 — it's 0x0001. And at offset 6, 2. Version 1.2.

Read them the wrong way and you get version 256.512, which is absurd.

Strings are unaffected — an array of single bytes has no byte order to get wrong. That's why text reads left-to-right in a hex dump while numbers look reversed.

An implausible result is a gift.

It tells you immediately that you made an error. Enormous numbers, negative lengths, timestamps in the year 30,000 — check byte order first.

The errors that cost you a day are the plausible ones.

Those you catch by checking against something independent, not by noticing they look odd.

An open question

There's a length field at offset 8. Compared to the actual file size, it doesn't match — the file is larger than the length claims.

Possible: the length excludes the header. The data is compressed. There's a checksum or signature appended after the payload.

We don't have enough information to decide. The correct action is to write the question down and continue.

An unresolved question that has been recorded is a normal state of work. One that's been silently forgotten is how you end up with a wrong model of the program.

This one stays open until Lecture 9.

Write it on the standing OPEN QUESTIONS board. It stays up all course and gets crossed off in L9. Five months to close the loop.

The obvious objection

A machine can already do most of this

It will solve a strings crackme instantly, read assembly faster than you, and produce a fluent explanation of any function.

So why learn it?

The answer is slide 8

Compilation destroys information, so recovering intent is inference, not lookup.

A tool that produces the most likely explanation is genuinely useful — and it is wrong specifically where the program departs from what is likely.

Obfuscated code, unusual constructs, deliberate misdirection, custom algorithms: all, by construction, unlikely.

That's not a defect being patched. It's the shape of the problem.

The failure has a particular shape

Wrong output does not arrive labelled as wrong. It arrives with the same fluency and confidence as correct output.

Show a model only the strings output of a stripped binary and it will frequently narrate a detailed account of the program's behaviour, built from a handful of format strings.

Coherent. Specific. Plausible. Substantially invented.

This is the session's Falsification Drill. Take a student's actual model output and run it: state the claim, name what would falsify it, make the observation, record the verdict on the scoreboard.

The standard, for the rest of the course

For any claim about a binary:

What observation would show
this to be false?

Then make that observation.

  • A claim about a string → check the bytes
  • A claim about a comparison → check the disassembly
  • A claim about behaviour → check in a debugger

This is not a special procedure for machines

It's the ordinary discipline of the field, and it applies identically to your own hypotheses — which will also be confident, and also sometimes wrong.

The tool has not changed what the work is.

It has made the ability to verify the scarce part.

Summary

  • RE is inference from evidence, not recovery of source
  • Compilation is one-way and many-to-one — distinguishing information is genuinely gone
  • What survives is what the machine needs to run. That's your leverage
  • file is a hypothesis; xxd is evidence
  • strings is the best first move and strands you when it fails, because it never told you why it worked
  • x86 is little-endian. Implausible values usually mean byte order
  • Record open questions rather than forgetting them
  • Any claim — yours or a machine's — is checked by naming the observation that would falsify it
