The skill is not reading code

You can read instructions, follow control flow, recover types, drive a debugger, read a binary's structure. None of that is yet reverse engineering.

The reason is scale. aurad has a few thousand instructions. A browser has millions.

You read maybe two percent. The craft is choosing which two percent.

That choice depends on your goal.

"Where does it validate the licence" and "does it send my data anywhere" and "why does it crash on this input" point at completely different two percents of the same binary.

No tool knows your goal.
The triage is yours.

Triage: five steps before any code


1. What is it?         file, readelf   — arch, linkage, stripped?
2. What does it touch?  strace/ltrace   — files, network, environment
3. What can it say?     strings         — errors, formats, banners, paths
4. What does it call?   PLT list        — crypto? network? both?
5. Where is my target?  xref a string / import → the code

   THEN read code — only the part triage pointed you at.

Amateurs open the disassembler at address zero and scroll. Professionals spend five minutes on 1–5 and open it at the one function that matters.

Watch: a string to the target

strings aurad | grep -i "command" "bad command" → xref "bad command" → the function that prints it → reached from the dispatcher → which validates before dispatching

Under a minute, from a string, to the exact function — in a binary you've never opened, reading nothing irrelevant.

The strings and imports are a map. Triage is reading the map before setting out.

The hypothesis loop


     ┌──────────▶  FORM a hypothesis  ──────────┐
     │           "this loop is a checksum"        │
     │                                            ▼
  RECORD it                                  PREDICT what you'd
  (confirmed /                               observe if true
   killed /                                  "sum of input bytes"
   still open)                                    │
     ▲                                            ▼
     └──────────────  TEST it  ◀──────────────────┘
              (feed known input, read the value)

The scientific method with a debugger attached.

The two steps everyone gets wrong

PREDICT does the intellectual work.

"This is a checksum" is not testable. "This is a checksum, so four zero bytes give zero and one one-byte gives one" is testable — and confirms or kills the idea in seconds.

RECORD is the one everyone skips.

  • You will not remember in two weeks, with no homework in between
  • A finding you can't reproduce is not a finding
  • A written-down dead end is a real result — it stops you (and the next person) going there again

The notebook is not bureaucracy. It's what separates an investigation from thrashing.

Knowing when to switch

Read (static) until you hit a value you can't compute by inspection — derived from input, read from a file, too tangled to follow.

Then run it.

Run (dynamic) until you need a path this execution didn't take, or you have a value and want to know where it came from.

Then read it.

The mistake in both directions is stubbornness — computing an inlined transform in your head when a breakpoint would hand it to you; single-stepping thousands of instructions when reading shows the shape at a glance.

Recognise algorithm shapes

AlgorithmThe tell
AESS-box: 256-byte table starting 63 7c 77 7b
SHA-256init values 6a09e667 bb67ae85; 64-round loop
MD5constant 67452301
base64the alphabet string; >>6, & 0x3f
CRC32256-entry table; xor-and-shift per byte

Structural: a state machine is a switch on a state var in a loop; a parser has an advancing cursor and character-class checks; a protocol handler reads a length, then that many bytes.

Recognise, then look up. You don't reconstruct AES — you recognise its fingerprint and read the spec.

The deliverable is not "the answer"

For a licence algorithm, "the key is validated by a rolling hash" is not the deliverable.

The deliverable is: the address of the transform, the exact recurrence, the inputs you fed and outputs you saw, the hypotheses you killed, and enough that a reader could write the keygen from your notes.

A finding you can state but not support is a guess. A finding documented with its evidence is knowledge. That difference is the entire value of the work.

On ground truth you built yourself, minutes ago

Hand the model the decompilation

Ask for the exact algorithm. It produces something fluent and mostly right: "a CRC32 of the key", or a rolling hash with a plausible rotation.

Genre correct. Structure correct. It recognised the shape — the same recognition slide 8 is about.

The specific constant is wrong.

The check is decisive — you already did the work

key "AAAA" through the model's claimed algorithm: acc after 2 bytes = 0x1e2f key "AAAA" through the real binary: acc after 2 bytes = 0x3b7c ↑ diverged

A plausible member of the "licence hash" family — right family, wrong function — because it pattern-matched common implementations instead of tracing this one.

Falsification Drill, highest stakes of the course — the class built the ground truth themselves, live, minutes ago. Score the model's answer against the real recurrence on the board.

The whole course in one observation

The model got you ninety percent there in one second: it correctly said "rolling hash" — genuinely useful, and faster than you.

The last ten percent was a rotation constant. It was wrong. It would have broken every key you generated.

You caught it in ten seconds — because you had the real recurrence to compare against.

You don't reject the tool. You don't trust it.

You use it for the ninety percent, and you are the ten percent.

And the only thing that lets you be the ten percent is that you can produce the ground truth the tool cannot.

Summary

  • The skill is choosing which 2% to read. It depends on your goal, so it can't be delegated
  • Triage in five steps before reading any code. Reach the target by xref'ing a string or import
  • The loop: form, predict, test, record. Predict does the work; record makes it reproducible
  • Switch static↔dynamic deliberately. The mistake is stubbornness
  • Recognise algorithm shapes by constants and structure. Recognise, then look up
  • The specialised zoo is recognise-and-look-up, never memorise — and where an assistant is most useful
  • The deliverable is a documented, reproducible finding, not an answer
  • On ground truth you built: the tool gives right family, wrong constant. You catch it only because you have the real recurrence
