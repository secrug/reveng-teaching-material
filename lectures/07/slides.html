Reverse Engineering · Lecture 7

Dynamic analysis:
running it and watching it

A breakpoint is a hypothesis test.
A patch is an experiment. Neither is a victory.

Second painful session for ARM Macs — single-stepping under emulation. Tier-1 shared box mandatory. Verify ltrace actually runs in the image beforehand; it's often missing or flaky in containers.

Two kinds of question

Static

Reading without running.

What can this program do?

All paths. Imprecise values.

Dynamic

Running and observing.

What does it do, with this input, right now?

One path. Exact values.

Neither replaces the other. Real work alternates: read until you have a hypothesis, run to test it, return to reading with what you learned.

What a running program is


0x7fff...  ┌──────────────┐  high
           │    stack     │  grows down   (Lecture 4)
           │      ↓       │
           │   [libc]     │  mapped shared library
           │      ↑       │
           │    heap      │  grows up     (Lecture 5)
           ├──────────────┤
           │ .bss  .data  │  globals
           │ .rodata      │  constants
           │ .text        │  your code
0x400000   └──────────────┘  low

Every process believes it has the machine to itself. Addresses in one process mean nothing in another.

See the real thing

(gdb) info proc mappings Start Addr End Addr Perms objfile 0x555555554000 0x555555555000 r--p /home/s/auractl 0x555555555000 0x555555556000 r-xp /home/s/auractl ← code 0x7ffff7d95000 0x7ffff7f1d000 r-xp /lib/libc.so.6 0x7ffffffde000 0x7ffffffff000 rw-p [stack]

Ground truth about what is loaded and where. The first thing to check when an address makes no sense.

Syscalls: the boundary

Your code runs in user mode. It cannot touch the disk, the network, or the screen. Only the kernel can.


    mov  eax, 1          ; syscall 1 = write
    mov  edi, 1          ; fd 1 = stdout
    mov  rsi, msg        ; buffer
    mov  edx, 13         ; length
    syscall              ; trap into the kernel

printf is not magic. It formats a string in user space and eventually calls write. libc is a library of convenient wrappers around these traps.

The syscall boundary
cannot be avoided.

A program that reads a file must issue openat and read — however obfuscated the rest of it is.

That makes syscalls an excellent observation point. And the numbers are fixed by the kernel ABI, so they survive everything compilation does.

ASLR

Stack, heap and library addresses are randomised every run. Address space layout randomisation exists to make Lecture 4's return-address attack harder: you can't redirect control to something you can't locate.

Practical consequence: addresses differ between runs. Yours won't match your neighbour's.

gdb disables it so debugging is reproducible — helpful, and occasionally misleading.

Record offsets from a known base, not absolute addresses. And note whether an address was observed under gdb.

The fact that turns a debugger into a mechanism

How a breakpoint actually works

gdb overwrites the byte at that address with 0xCC — int3, a one-byte software interrupt.

Execution reaches it, the CPU traps into the kernel, the kernel stops the process and notifies gdb. gdb puts the original byte back so the program looks untouched, and restores it when you continue.

Look at it

(gdb) x/1bx $pc 0x401136: 0x55 (gdb) break *0x401136 (gdb) # ... while the program is running: (gdb) x/1bx 0x401136 0x401136: 0xcc ← int3
This is the wow moment. Spend on it. Seeing 0xCC in their own program's bytes is when the debugger stops being magic. Pays off directly in L9's anti-debug segment.

Two consequences

A program can detect this. If it reads its own code and finds 0xCC where it expects something else, it knows it's being debugged.

A standard anti-debugging technique — and you now understand it completely rather than as a mysterious trick. More in Lecture 9.

Hardware watchpoints are a different mechanism. The CPU has debug registers holding a few addresses; it traps when any is read or written. No bytes are patched.

That's how you answer "what is writing to this variable?" — otherwise you'd have to find every possible writer by hand.

Limitation: four debug registers, so four hardware watchpoints.

The toolkit


break f / b *0xADDR       set a breakpoint
break f if x == 5         conditional — only stop when it matters
tbreak                    temporary: fires once, removes itself
watch  <expr>             stop when the value changes (hardware)
rwatch <expr>             stop when it is read

run / continue            start / resume
si / ni                   step one instruction / step over calls
finish                    run until this function returns

info registers [reg]      register state
x/8gx  $rsp               8 giant-words in hex
x/20i  $pc                20 instructions
x/s    $rdi               as a string

Most debugger skill is stopping
at the right moment.

A breakpoint in a loop that runs ten thousand times is useless.

The same breakpoint with if i == 9999 is precise.

And sometimes: don't stop at all


break *0x401156
commands
  silent
  printf "acc = %#x\n", $rax
  continue
end

Logs a value every time the location is hit, without pausing.

For anything more complex, gdb embeds Python — a gdb.Breakpoint subclass whose stop() returns False logs and continues.

Turning a manual observation into an automated trace is one of the highest-leverage moves available.

Before attaching anything: watch the boundaries


strace ./program        # every system call
ltrace ./program        # every library call

strace — which files it opens, what it reads and writes, whether it hits the network, what environment variables it checks.

Thirty seconds of strace often answers "what does this thing even touch?" better than an hour of reading.

ltrace is less reliable — it depends on calls going through the dynamic linking mechanism (Lecture 8), and misses anything inlined or statically linked.

Patching


je   (0x74)  ↔  jne  (0x75)     invert a branch
any jump     →  nop  (0x90)     delete a branch
function     →  ret  (0xc3)     stub it out entirely
  

f = open('program', 'r+b')
f.seek(0x1189)          # file offset of the je
f.write(b'\x75')        # make it jne
f.close()

One byte. The licence check passes. Permanently, on disk, no debugger.

It feels like winning.

It is an experiment.

Flipping a branch tests the hypothesis "this branch is the check."

Program behaves as expected → hypothesis supported.
Crashes three functions later → the check has a second part. Also a result.

Two ways to defeat a licence check

The cheap way

Break on the comparison, flip the flag, it prints "Valid".

Two minutes.

What you now know: nothing. You can't produce a valid key, you don't know what makes one valid, and a second check will blindside you.

The real way

Read both operands. One is from your input; one is computed. Where from? Watchpoint on it.

Written after a loop over your input. Characterise it — sum? shift-and-xor? Feed known inputs, watch the accumulator.

Now you can state what a valid key must satisfy. And construct one.

If your solution only works on this binary, you reverse engineered the binary.

If it works on any input, you reverse engineered the algorithm.

Channel the patching euphoria here. The Boss tier bans patching on purpose — a student who can only patch has disabled a check, not understood it.

Lab — 40 + 30 minutes

Break, watch, understand

Core — break on the comparison. Report what is compared to what, and where the expected value came from. Not "make it say valid."

Stretch — watchpoint on the derived key; report every write and by what.
Boss — hand-compute a valid key. No patching. Then patch it, and write why the patch is the inferior solution.

Lab B: a gdb Python script that logs the transform's input byte and running accumulator.

The realistic use of assistance

"Write me the gdb script"

Not "explain this binary." "Write the script that logs the accumulator each iteration."

That's a genuinely good use: boilerplate, fiddly syntax, faster to generate than to write.

What comes back is about ninety percent right.

And one detail is wrong

  • It reads $rax when the accumulator lives in $rbx at that point
  • Or it hooks the top of the loop body, sampling before the round updates it — every value one iteration stale
  • Or a commands block with no end, and nothing runs at all

The third you notice immediately.

The first two you don't — the script runs, prints a table of plausible numbers, and you analyse a trace in which every value is wrong.

Falsification Drill: run it on a known 4-byte input, count the lines / check the values against a manual read. The artifact under test today is AI-generated TOOLING, not an AI analysis — the most realistic case.

The fix takes ten seconds

— if you know where the value actually lives.

If you don't, you re-prompt. And you get another plausible script with a different subtle error, because the model has the same blind spot each time and no access to the running program to check against.

Not "AI cannot reverse engineer."
"AI writes tooling that is 90% right, and the 10% silently invalidates the output."

You are not competing with it. You are the part of the loop that can check it — and that requires knowing which register holds what.

Which is Lecture 2.

Summary

  • Static: all paths, imprecise. Dynamic: one path, exact. Real work alternates
  • info proc mappings is ground truth about what's loaded where
  • A syscall is the user/kernel boundary and cannot be avoided — an excellent observation point
  • ASLR randomises per run; gdb disables it. Record offsets, not addresses
  • A software breakpoint is an int3 (0xCC) byte patch — which is why a program can detect it
  • Hardware watchpoints patch nothing and answer "who writes here?". There are four
  • Most debugger skill is stopping at the right moment. Conditional breakpoints; scripts that log without stopping
  • strace/ltrace first: what does it touch?
  • A patch is an experiment, not a victory
  • Generated tooling is 90% right; the wrong 10% is usually a register or a sample point, and it invalidates every number
