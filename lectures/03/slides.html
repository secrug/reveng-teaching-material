Reverse Engineering · Lecture 3

Control flow:
decisions and loops in machine code

The compiler has a small, finite vocabulary. Learn it and you read it backwards.

Longest warm-up of the course (15 min) — four weeks since the machine model, no homework bridging it. Hand-trace 8 instructions hitting the L2 sticking points: zero-extension, lea as arithmetic, xor zeroing, test. Verify in gdb on screen.

The machine has no if

No while, no for, no switch. One mechanism: conditionally write a new value into rip.

Every control structure you have written compiles to some arrangement of compares and jumps.

But the compiler doesn't invent a new arrangement each time. It has a vocabulary — a handful of shapes per construct.

This lecture is that vocabulary.

Conditional jumps

After cmp a, bJumpTaken when
je / jza == b
jne / jnza != b
signedjl jle jg jge less / greater
unsignedjb jbe ja jae below / above

Signed and unsigned comparisons use different instructions. The compiler had to choose — and its choice records the signedness of a variable whose type was destroyed.

Same leverage as movzx/movsx in L2. Collect these as they accumulate.

The most common misreading in the course

The compiler branches on the negation


if (x > 5) {
    do_something();
}
    

    cmp  DWORD PTR [rbp-4], 5
    jle  .Lskip     ; x <= 5 → skip
    call do_something
.Lskip:

Source said >. Assembly says jle, which is ≤. Not a contradiction — the jump means "get me out of here if the condition failed."

Read a conditional jump as the exit condition, never the source condition.

Say this three times today. Put it on the board and leave it there. Students misread it for a month otherwise, and every downstream conclusion inverts.

Basic blocks

A maximal straight-line run with one entry, one exit. Blocks end at any jump and begin at any jump target.


        ┌──────────┐
        │   B0     │  cmp / jle ──┐
        └────┬─────┘              │
             │ fall through       │
        ┌────▼─────┐              │
        │   B1     │              │
        └────┬─────┘              │
             └────────────▶┌──────▼───┐
                           │   B2     │
                           └──────────┘

That is an if without an else — identified without reading a single instruction inside B1.

Stop reading instructions.
Start reading blocks.

The instructions inside a block are rarely the interesting part. The shape of the graph is.

Largest single speed-up available to you. Costs nothing but the habit.

Lecture 2's line-by-line annotation was the last time you should read that way.

Shape 1–2: if, if/else

if, no else


    cmp  eax, 5
    jle  .Lend
    <body>
.Lend:

if / else


    cmp  eax, 5
    jle  .Lelse
    <if body>
    jmp  .Lend
.Lelse:
    <else body>
.Lend:

The unconditional jmp at the end of the first body is the tell. Without it, there is no else.

Shape 3–4: while, for


    jmp  .Ltest        ; enter by jumping to the test
.Lbody:
    <body>
.Ltest:
    cmp  eax, ebx
    jl   .Lbody

The test sits at the bottom. Looks inside out — and there's a reason: one conditional jump per iteration instead of a conditional plus an unconditional. Cost is one extra jump on entry.

for is this shape with an initialiser before it and the increment at the end of the body. There is no for in machine code — it's a while with bookkeeping.

Shape 5: do/while


.Lbody:
    <body>
    cmp  eax, ebx
    jl   .Lbody

There is no jump at the top.
That absence is the entire signature.

A while enters by jumping to its test. A do/while falls straight into its body — because it must run at least once.

Shape 6: the decision with no branch


int max(int a, int b) {
    return a > b ? a : b;
}
    

    cmp   edi, esi
    mov   eax, esi
    cmovg eax, edi
    ret

cmovg writes the source only if the condition holds — without branching. A mispredicted branch costs far more than an always-executed move.

A decision in the program can have
no jump in the machine code.

If you locate control flow by searching for jumps, you will miss it entirely.

Also why constant-time crypto is written this way: no branch means no timing difference that depends on the secret.

Short-circuit && and ||


if (p != NULL
    && p->count > 0) {
    ...
}
    

    test rdi, rdi
    je   .Lskip
    cmp  DWORD PTR [rdi+8], 0
    jle  .Lskip
    <body>
.Lskip:

Two separate tests, both jumping to the same label. || is the mirror image — each test jumps into the body on success.

The second condition is only reachable through the first. When you ask "can this dangerous code be reached?", the chain of short-circuit tests is the set of conditions that must all hold.

switch has three compilations

Case valuesCompiles to
Dense (0–20)Jump table — index into a table of targets
Sparse (1, 900, 40000)If-chain — sequential comparisons
Many, scatteredBinary search — a tree of comparisons

"I found a jump table" tells you the case values were dense.

"I found an if-chain" tells you nothing about whether the programmer wrote switch or if.

Which construct was typed is among the things compilation destroys.

The jump table, line by line


    cmp  edi, 0x63
    ja   .Ldefault              ; bounds check (unsigned!)
    mov  eax, edi
    lea  rdx, [rip+0x1e4c]      ; address of the table
    movsx rax, DWORD PTR [rdx+rax*4]   ; entry = 4-byte SIGNED offset
    add  rax, rdx               ; offset + table base = target
    jmp  rax                    ; indirect jump

The check is unsigned on purpose: a negative index reinterpreted as unsigned becomes enormous and fails too. One comparison handles both ends.

Live on auractl's dispatcher. Scripted wrong turn: compute the RIP-relative table address from the CURRENT instruction, land in garbage, notice, go back and fix. Narrate the recovery.

Why the table holds offsets, not addresses

32-bit signed offsets from the table's own base — half the size of 64-bit addresses, and position-independent.

movsx sign-extends because targets can lie before the table.

The bounds check is the entire safety of this construction. If it's missing or wrong, the program indexes past the table and jumps to whatever it finds.

You can now recognise its absence. That's a serious class of vulnerability.

Where the tools are most useful — and most quietly wrong

Reconstruction is their best trick

Give a decompiler or a model a function's disassembly and you get readable C with the loops and conditionals in roughly the right places, in a second. Usually correct.

The failure mode is narrow and specific:

loop bounds.

One character

the binary


cmp  eax, edx
jle  .Lbody     ; ≤  → runs n+1 times

the reconstruction


for (int i = 0; i < n; i++)
                  // runs n times

The common idiom is <. A tool producing the most likely reconstruction emits <.

It compiles. It reads naturally. It is wrong by one iteration.

Nothing about that output looks suspicious. It isn't garbled or hedged. It's a perfectly ordinary loop.

The check takes thirty seconds

(gdb) b *0x401156 # the loop body (gdb) run 5 (gdb) info breakpoints breakpoint already hit 6 times

n = 5, body ran 6 times → the bound is ≤.

Requires nothing beyond the ability to find the body.

Falsification Drill: state the claim, ask the room for the falsifying observation (count iterations), make it, record verdict + reason. The reason: the model produced the statistically common loop, not the one in front of it.

Off-by-one in a loop bound

Historically among the most productive sources of security vulnerabilities in real software.

The difference between < and ≤ is the difference between writing inside a buffer and writing one element past it.

Getting that boundary exactly right is not pedantry.

Summary

  • One mechanism: conditionally write to rip
  • Signed vs unsigned jumps recover a type the compiler erased
  • The compiler branches on the negation — read the exit condition
  • Read basic blocks, not instructions. The graph shape is the information
  • Six shapes cover almost everything. do/while is identified by the absence of a top jump
  • cmov: a decision can exist with no jump at all
  • A jump table's bounds check is its entire safety; entries are signed offsets, not addresses
  • At -O2, loops are rotated, unrolled, stripped of counters
  • Tools are reliable on shape, unreliable on bounds. Count the iterations
