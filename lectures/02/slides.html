The machine:
registers, memory, instructions

A CPU is a state machine. Nothing more mysterious is happening, ever.

Warm-up first (15 min): five retrieval questions from L1 — what survives compilation, file vs xxd, why no perfect decompiler, the AURA magic bytes, the open question on the length field. Settle them by doing, not telling.

The whole machine


┌─────────────── CPU ───────────────┐      ┌──── MEMORY ────┐
│ rax rbx rcx rdx rsi rdi rbp rsp   │      │  one flat      │
│ r8  r9  r10 r11 r12 r13 r14 r15   │◀────▶│  array of      │
│ rip                               │      │  bytes         │
│ flags:  ZF  SF  CF  OF            │      │                │
└───────────────────────────────────┘      └────────────────┘

Every instruction is a function from that state to a new state. There is nothing else.

Three things that contradict your C intuition

  • Memory has no types. A byte is a byte. int, double, char*, struct account do not exist here — only an address, a width, and an operation
  • There are no variables. A variable was a name for a register or a stack slot. After compilation: the register or slot remains, the name does not
  • rip is an ordinary register that usually increments. Control flow is writing a different value into it

Almost everything interesting in RE and in security comes from the word usually.

The register file

rax rbx rcx rdx rsi rdi rbp rsp and r8–r15

The first eight carry names from the 16-bit 8086 of 1978: accumulator, counter, source index, destination index. On x86-64 that's mostly history — rax is not special to the hardware.

Two keep meaning by convention:

  • rsp — stack pointer. Modified implicitly by push/pop/call/ret
  • rbp — frame pointer

Both are Lecture 4. Which register holds what is otherwise the compiler's choice — except where the calling convention forces it, and that constraint is what makes signatures recoverable.

Four widths, one register


 63                    31        15     7    0
 ├──────────────────────┼─────────┼──────┼────┤
 │                     rax                    │   64-bit
                        │        eax          │   32-bit
                                  │    ax     │   16-bit
                                        │ al  │   8-bit

Same pattern throughout: rbx/ebx/bx/bl, r8/r8d/r8w/r8b

Memorise this one

Writing to a 32-bit register zeroes the upper 32 bits of the full register.

Writing to a 16-bit or 8-bit register leaves the upper bits unchanged.

Watch it happen


mov rax, 0xffffffffffffffff   ; rax = 0xffffffffffffffff
mov eax, 1                    ; rax = 0x0000000000000001   ← upper half zeroed
mov ax,  2                    ; rax = 0x0000000000000002   ← upper bits preserved
mov al,  3                    ; rax = 0x0000000000000003   ← upper bits preserved
Do this live in gdb with the register window up. Nobody believes it otherwise. Audible reaction on line 2.

There is no principle here

AMD made this decision designing the 64-bit extension, for instruction-encoding efficiency: zero-extension avoids a prefix in the common case. The 16- and 8-bit forms kept the old behaviour for backward compatibility.

You cannot derive it. You either know it or you don't.

Remember that this rule is arbitrary. We come back to it at the end of the lecture for a reason.

Memory: two operations


mov rax, [rbx]     ; LOAD:  rax = the 8 bytes at address rbx
mov [rbx], rax     ; STORE: write rax's 8 bytes to address rbx

Brackets mean "go to memory". No brackets means the register itself.

Width comes from the register, or is stated when ambiguous:


mov eax, [rbx]               ; load 4 bytes
mov al,  [rbx]               ; load 1 byte
mov DWORD PTR [rbx], 5       ; store 4 bytes
mov BYTE PTR  [rbx], 5       ; store 1 byte

Narrow value, wide register


movzx rax, BYTE PTR [rbx]    ; zero-extend: upper bits become 0
movsx rax, BYTE PTR [rbx]    ; sign-extend: upper bits copy the sign bit

The byte 0xFF:
movzx → 255    movsx → −1

The instruction the compiler chose tells you whether the source variable was signed — information the type system carried and then discarded.

First instance of the Lecture 1 principle in action: the compiler had no choice, so the choice is evidence.

The twenty that matter

Over a thousand instructions exist. These are ~90% of compiled code.

Two idioms — read as single units

xor eax, eax

Sets eax to zero. Anything XORed with itself is zero. Two bytes to encode instead of five for mov eax, 0.

test rax, rax

Asks "is rax zero?". ANDing a value with itself changes nothing, so the only useful output is the flags.

Neither is obfuscation. Both are everywhere. Stop decoding them and start recognising them.

Addressing modes


[ base + index*scale + displacement ]        scale ∈ {1, 2, 4, 8}
  

[rbx]                  ; the 8 bytes at rbx
[rbx + 8]              ; at rbx+8
[rbx + rcx*4]          ; at rbx + 4*rcx
[rbx + rcx*8 + 16]     ; at rbx + 8*rcx + 16
[rip + 0x2e4a]         ; relative to the NEXT instruction — a global

The hardware computes all of that in one instruction. That's why the form exists: array indexing is one operation, not three.

The scale field is free
type information.

A variable index times 4 means an array of 4-byte elements. Times 8, 8-byte elements or pointers.

A constant displacement with no index usually means a struct field.

The compiler was obliged to emit it correctly. Lecture 5 builds type recovery on exactly this.

RIP-relative, and the trap

[rip + 0x2e4a] is how modern code refers to globals and constants. Position-independent code needs it: the program doesn't know where it will be loaded, but it always knows the distance from one part of itself to another.

The offset is relative to the address of the next instruction — not the current one.

Compute from the wrong base and you land somewhere plausible-looking and entirely wrong.

This catches everyone exactly once. Make it today.

lea is arithmetic, not memory


lea rax, [rbx+8]    ; rax = rbx + 8            (compute the address)
mov rax, [rbx+8]    ; rax = the value at rbx+8 (go and fetch it)

Load effective address: compute what the addressing mode describes, put it in a register, never touch memory.

The compiler's pocket calculator


lea rax, [rdi + rdi*2]      ; rax = rdi * 3
lea rax, [rdi*8 - 4]        ; rax = rdi * 8 - 4
lea rax, [rdi + rsi]        ; rax = rdi + rsi   (a three-operand add)

None of these touch memory. None are about addresses. The addressing unit is fast and doesn't disturb the flags, so compilers use it to do sums.

When you see lea, do not assume a pointer. Read the brackets as an arithmetic expression.

Flags

FlagSet when
ZF zerothe result was zero
SF signthe top bit was set (negative, if signed)
CF carrycarried/borrowed out of the top bit (unsigned overflow)
OF overflowoverflowed as a signed value

cmp a, b computes a - b purely to set these, then throws the subtraction away. If a == b the result is zero, so ZF is set.

That is how equality is tested: subtract, and ask whether the answer was zero.

The comparison and the branch are separate

Two instructions, not one. Other instructions in between can overwrite the flags.

When tracing, the flags at the jump are the ones set by the most recent flag-modifying instruction — which is not always the cmp sitting directly above it.

Which conditional jump reads which flag is Lecture 3.

Lab A — 40 minutes · first 12 laptops closed

Be the CPU

Core — hand-trace 20 instructions on paper. Then verify in gdb.

If they disagree, find the first instruction where they diverged — don't redo the whole trace.

Stretch — trace with memory and lea; hand-decode 5 instructions from raw bytes.
Boss — one instruction's operand size changes the final answer. Find it.

Enforce the closed laptops physically — walk the room. Watch for students who assume they're wrong when gdb disagrees; often gdb is exposing their zero-extension error, which is the whole point. Bisection is the skill.

Reading a real function


sum_array:
    xor  eax, eax                    ; total = 0
    xor  ecx, ecx                    ; i = 0
.loop:
    cmp  ecx, esi                    ; compare i with n
    jge  .done                       ; if i >= n, finish
    add  eax, DWORD PTR [rdi+rcx*4]  ; total += arr[i]
    add  ecx, 1                      ; i++
    jmp  .loop
.done:
    ret                              ; return total in eax

What we just recovered

  • Two registers zeroed at entry → one accumulates, one counts
  • [rdi + rcx*4] → rdi is the base of an array of 4-byte elements, rcx is the index
  • rdi is arg 1, rsi is arg 2 (L4) → a pointer and a count
  • eax holds the result at ret → returns a 4-byte integer

int sum_array(int *arr, int n)

No symbols. No source. Recovered from instruction widths and an addressing mode.

None of that was written
by a programmer.

The *4, the 32-bit register names, the argument registers — all of it was forced on the compiler by the machine.

That is where your leverage always comes from.

-O0 versus -O2

-O0

Every local has a stack slot. Reading a variable is a load from [rbp-N]; writing is a store. Verbose, maps almost line-by-line onto source.

-O2

Locals live in registers. Loads and stores largely vanish. sum_array was this shape — nothing touches the stack, the loop variable never has an address.

-O0 examples can mislead. Production binaries look like the second kind. We use both deliberately.

Lab B — 30 minutes

Instruction archaeology

Take objdump -d of one function and annotate every line in plain English. About 30 instructions.

Tedious on purpose. It's the last time you'll read line-by-line — from Lecture 3 you read in blocks — and doing it once at full resolution is what makes block-reading possible.

The obvious objection, again

A debugger does this instantly

So why trace twenty instructions by hand?

Because the debugger tells you the answer and nothing else.

Tracing by hand builds the model that lets you predict the answer — which is what you need for code you cannot run: a function deep in a stripped binary, a branch that only fires under conditions you can't reproduce, a fragment quoted in a report.

Reading assembly fluently means knowing what it will do without executing it.

And there's a second reason

Look back at what this lecture contained:

  • The zero-extension rule
  • Which registers exist, and their names
  • The encoding of addressing modes
  • RIP-relative measuring from the next instruction
  • xor eax, eax as the idiom for zero

All of it is arbitrary. None of it follows from first principles.

Which is exactly where automation fails

Ask a model for the final register state of a short sequence. It will usually track the arithmetic correctly — and then report a full 64-bit value where the hardware zeroed the upper half.

The arithmetic is the part that follows from general principles.
The zero-extension rule is the part that does not.

Confident. Internally consistent. Wrong in one specific place.

You catch it with info registers — and only if you knew the rule existed.

Falsification Drill: state the claim, ask the room what observation would falsify it (one: info registers at the final instruction), make it, record the verdict and the reason on the scoreboard. The reason column is the valuable one.

Summary

  • State = 16 registers + rip + flags + a flat byte array. Nothing else
  • Memory has no types. Types were compiler fiction, discarded
  • 32-bit writes zero the upper half; 16- and 8-bit writes do not
  • movzx vs movsx reveals whether the source was signed
  • [base + index*scale + disp] — the scale is the element size, free
  • RIP-relative is measured from the next instruction
  • lea computes without accessing memory; mostly it's arithmetic
  • cmp/test set flags and discard the result; the branch is a separate instruction
  • Hand-execution builds prediction — and this material is arbitrary, so it must be known rather than derived
