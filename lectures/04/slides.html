The stack, calling conventions,
and functions

Every function announces its own signature in the way it touches registers.

Dense session, will run long — pre-plan cuts: Lab A Boss first, then tail calls/red zone. Protect the recursion demo and the ABI drill. Issue reference card #3 at the start.

The CPU has no idea what a function is

It has call and ret — jumps that remember where they came from — and a register conventionally used as a stack pointer.

Arguments, return values, locals, scope: all of it is an agreement between the compiler and everything it must interoperate with.

On 64-bit Linux that agreement is the System V AMD64 ABI. Documented, fixed, mandatory.

The compiler had no choice about it. Which is why a stripped function still announces its own signature.

The stack is just memory


  high addresses
  ┌────────────────────┐
  │  caller's frame    │
  ├────────────────────┤
  │  return address    │  ← placed here by `call`
  │  saved rbp         │  ← rbp points here
  │  local a  [rbp-8]  │
  │  local b  [rbp-16] │
  └────────────────────┘  ← rsp (top of stack)
  low addresses              grows DOWNWARD

No special hardware structure. No protection. No type. rsp holds the address of the top.

Four instructions, defined by rsp


push rax   ≡   sub rsp, 8       ;  mov [rsp], rax
pop  rax   ≡   mov rax, [rsp]   ;  add rsp, 8
call f     ≡   push (address of next instruction)  ;  jmp f
ret        ≡   pop rip

Read the last two again.

call pushes the address to come back to. ret pops it into rip.

The return address is ordinary data
sitting in memory.

Nothing marks it as special.

If something writes to that location, the function returns somewhere else.

Hold that thought for ninety minutes.

The ABI — the parts you need


Integer / pointer arguments, in order:
    rdi   rsi   rdx   rcx   r8   r9      then the stack
     1     2     3     4     5    6

Return value:     rax            (rdx:rax for 128-bit)
Floating point:   xmm0-xmm7 args, xmm0 return

Callee-saved:     rbx rbp r12 r13 r14 r15   (must be preserved)
Caller-saved:     rax rcx rdx rsi rdi r8-r11 (may be destroyed)

Stack alignment:  rsp 16-byte aligned at the point of `call`
Red zone:         128 bytes below rsp, usable without adjusting rsp

No logic to the argument order. Memorise it. It's on card #3 and it'll be second nature within two sessions.

Callee-saved vs caller-saved

Some registers are guaranteed to survive a call. The rest may be destroyed by it.

A function wanting to use a callee-saved register must save and restore it — which is why prologues often open with push rbx.

That push is a signal: this function intends to keep something alive across a call it is going to make.

The technique this lecture exists to teach

A register that is read before it is
written was an incoming argument.

The value came from somewhere. The only somewhere is the caller.

Written before read → scratch space. A local, not a parameter.

Not a heuristic. It follows from a convention that was not optional for the compiler.

Applied to an unknown function


sub_401180:
    push rbp
    mov  rbp, rsp
    mov  DWORD PTR [rbp-0x14], edi   ; edi read → arg 1, 4 bytes
    mov  QWORD PTR [rbp-0x20], rsi   ; rsi read → arg 2, 8 bytes
    ...
    mov  eax, ...                    ; something meaningful in eax
    leave
    ret
  • rdx never read → no third argument
  • eax set before ret → returns 4 bytes

int sub_401180(int, void *)

No symbols. Never ran it. Disassembler only.

Arity is certain. Types are not.

An 8-byte argument might be a pointer, a long, or a size_t.

You find out by watching how it's used:

  • dereferenced → pointer
  • passed to strlen → char *
  • compared against a small number → a count

Keep these distinct in your notes. Overclaiming a type you merely suspect is the failure this course works hardest to prevent.

The classic -O0 frame


    push rbp            ; save the caller's frame pointer
    mov  rbp, rsp       ; establish ours
    sub  rsp, 0x20      ; reserve 32 bytes for locals
    ...
    leave               ; ≡ mov rsp, rbp ; pop rbp
    ret

With rbp fixed, every local has a stable address: [rbp-0x8], [rbp-0x10]…

Return address always at [rbp+8]. Caller's saved rbp at [rbp].

Build the offset table first. Then the function becomes legible.

At -O2 the textbook frame is often gone

What you'll see
Frame pointer omission rbp reused as a general register. Locals at [rsp+N] — and rsp moves, so the same local has different offsets at different points. Look for sub rsp, N: N is the frame size
The red zone 128 bytes below rsp are yours. A leaf function uses them without adjusting rsp. Writes to [rsp-8] look illegal. They aren't
Tail calls jmp to another function instead of call+ret. Not spaghetti — a call that reused the frame

The frame is a convenience the compiler can drop. The ABI is a contract it cannot.

Recursion needs no special machinery


fact:
    push rbx
    mov  ebx, edi            ; keep n in a CALLEE-SAVED register
    cmp  edi, 1
    jle  .Lbase
    lea  edi, [rbx-1]        ; n-1
    call fact                ; recurse — free to destroy rdi
    imul eax, ebx            ; result *= n   ← needs n to still be here
    jmp  .Ldone
.Lbase:
    mov  eax, 1
.Ldone:
    pop  rbx
    ret

The push rbx isn't decoration. It's what makes the multiply at the bottom correct.

Draw each frame on the board as it's pushed. Step three levels deep, then step out and watch them pop with rax carrying the product up. Recursion stops being scary the moment you can see the frames.

Two facts, already established

Putting them together

  1. call pushes the return address onto the stack
  2. Local variables live on the stack, immediately adjacent to it

Nothing distinguishes the return address from any other eight bytes.

Ninety seconds, in a debugger

(gdb) x/gx $rbp+8 # the saved return address 0x7fffffffe0c8: 0x0000000000401210 (gdb) set {long}($rbp+8) = 0x401196 # overwrite it (gdb) continue you win. # a function nobody called

No bug was exploited. I wrote to the stack in a debugger.

Now imagine the program writes past the end of a buffer that happens to sit just below it. Same effect, no debugger.

That is the buffer overflow.

A program that copies user input into a fixed-size stack buffer without checking the length hands the attacker control of rip.

We are not doing that field in this course.

But "memory layout" is now a security property, not an implementation detail — and stack canaries, NX, ASLR (Lecture 7) will make sense because you've seen what they defend against.

Lab B — 30 minutes

AURA-7 handler signatures

Take three command handlers from Lecture 3. Recover arity, argument types where visible, return type.

Required form: "handler 0x12 takes (char *path, int flags) and returns int — because it reads rdi as a pointer passed to strlen, reads esi and masks it, and rax holds a small integer at ret."

Evidence, then conclusion. Always that order.

Where the tools fail here

They under-count arguments

A function opens with strlen(rdi). Strongly recognisable pattern: string function, takes a string. The most likely signature is something f(char *).

Meanwhile rsi is read on the third instruction, before anything writes to it.

There are two arguments.

Not a failure of reading

A failure to keep reading after finding something familiar.

And invisible in the output: a plausible one-argument signature looks exactly like a correct one.

The check is §4 applied deliberately — for each of rdi rsi rdx rcx r8 r9, in order: read before written?

Definite answer. Under a minute. The ABI guarantees it's meaningful.

Falsification Drill. Get the falsifying observation from the room: "if there's a second argument, something reads rsi before writing it." Then check. Record verdict + reason: the model stopped at the first recognisable call.

Summary

  • A function call is a convention. The ABI was mandatory for the compiler, so it's readable evidence for you
  • The stack is memory; rsp points at the top; it grows down
  • call pushes a return address, ret pops it into rip. Nothing marks it special
  • Args rdi rsi rdx rcx r8 r9; return rax; callee-saved rbx rbp r12-r15
  • Read before written ⇒ incoming argument. That's how you recover arity from a stripped function
  • Arity certain, types likely. Record the difference
  • At -O2: no frame pointer, red zone, tail calls. The ABI still holds
  • push rbx in a prologue → a value must survive a coming call
  • Overwriting the saved return address redirects control — why memory layout is a security property
  • Tools under-count arguments. Check all six registers
