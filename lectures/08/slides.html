Formats, linking and loading

An executable isn't a monolith. It's a structured document the loader assembles into a process — and you can intervene without touching the code.

Same source. Same output. Why is one 50× bigger?

And which one still runs in ten years on a machine with different libraries?

An executable is a structured document

Not a stream of code. A file with a header, a table of contents, and distinct regions — assembled into a process by the loader.

On Linux the format is ELF. The same format serves three roles:

  • executables you run
  • shared libraries you link against
  • relocatable object files the compiler emits

readelf -h tells you which.

ELF is described twice


        ┌─────────────────────┐
        │    ELF header       │  "x86-64, entry 0x1050, ..."
        ├─────────────────────┤
        │  program headers    │  ◀── THE LOADER reads these
        │  (segments)         │      "map these bytes here, r-x;
        │                     │       those there, rw-"
        ├─────────────────────┤
        │   code and data     │
        ├─────────────────────┤
        │  section headers    │  ◀── THE LINKER + your TOOLS
        │  (.text .data ...)  │      "here is each named piece"
        └─────────────────────┘

Segments are for running. Sections are for linking and tooling.

Segments are for running.
Sections are for reading.

The loader maps segments with permissions and doesn't care about names. The running program never needs the section table.

So you can remove the section info and the program still runs. Stripping is an attack on the analyst, not the machine.

The sections that matter

readelf -h header readelf -l segments readelf -S sections readelf -d dynamic / NEEDED
.textcode
.rodataconstants, strings
.datainit globals
.bsszero globals (no file space)
.plt/.gotshared-call machinery
.symtabnames — stripped away
.dynsymdyn symbols — survive

That last distinction is the one to hold onto.

Relocation

Your program calls printf. The compiler doesn't know where printf is — it's in libc, loaded at an address not decided until runtime.

So it leaves a blank and attaches a note: "fill in printf's address here once you know it."

That note is a relocation. readelf -r lists them: each names a symbol and the location to patch.

Two ways to resolve them

Static

Library copied into the executable at build time. Resolved before it runs.

800 KB. Self-contained. Runs unchanged in ten years.

Dynamic

Library stays external. Records "I need libc" (NEEDED); the loader maps it in and resolves references at load time.

16 KB. Shared between processes. Needs a compatible libc present.

That 50× is entirely the presence or absence of libc inside the file.

PLT and GOT

How does a call reach a function whose address isn't known until runtime? One level of indirection.


  call printf@plt
        │
        ▼
  ┌── .plt ──┐         ┌──── .got.plt ────┐
  │ printf:  │──jmp──▶ │ [printf's slot]  │──▶ 1st call: resolver runs,
  │  jmp     │         │                  │             writes real addr here
  │ [GOT slot]         │                  │──▶ later:    jump straight there
  └──────────┘         └──────────────────┘

Lazy binding: nothing resolved until first use. A function never called is never resolved.

Watch the slot change

(gdb) x/gx 0x404018 # printf's GOT slot, before first call 0x404018: 0x0000000000401036 ← points back into the PLT (gdb) # ... step past the first printf ... (gdb) x/gx 0x404018 # after 0x404018: 0x00007ffff7e12420 ← a libc address. It changed.
This live demo is what makes lazy binding concrete. Don't just describe it — show the address change.

Three reasons to care

  • In a stripped binary, PLT entries are still named — strcmp, socket, connect. Dynamic symbols can't be stripped. A map into anonymous code
  • The GOT is a table of function pointers you can watch or overwrite — a debugging technique, and elsewhere an attack surface
  • It's the mechanism behind the interposition trick coming next

Interposition: LD_PRELOAD

Tell the loader: load my library first, and if I define a function with the same name as a library's, use mine.


int strcmp(const char *a, const char *b) {
    int (*real)(const char*,const char*) = dlsym(RTLD_NEXT, "strcmp");
    // observe or alter, then fall through if you like
    return real(a, b);
}
gcc -shared -fPIC hook.c -o hook.so -ldl LD_PRELOAD=./hook.so ./target

RTLD_NEXT = "the next strcmp after me" — how the hook calls the real one. The target binary is never modified.

Powerful — with a hard boundary

LD_PRELOAD only catches calls that actually go through the PLT to a shared library. It cannot touch:

  • inlined code — no call to intercept
  • internal functions — one of the program's own functions calling another doesn't cross the PLT
  • static linking — no dynamic call to interpose on
  • direct syscalls — bypass libc entirely

The boundary follows from lazy binding: it works on exactly the calls lazy binding resolves, and nothing else.

Ten minutes, transfer only

The same ideas in other clothes

Windows PE

Same structure, different names. The GOT's cousin is the Import Address Table. .dll not .so. LoadLibrary not the ELF loader.

objdump -x a PE and you'll recognise everything.

ARM64

Fixed 4-byte instructions. Registers x0–x30; args in x0–x7, return in x0.

Still a state machine, a stack, a calling convention. Lectures 2, 3, 4 are all true here.

If you thought you were learning x86, you were learning how machines work. That transfers.

Where the tool oversells

The textbook answer to a specific question

Ask a model how to bypass AURA-7's licence check with LD_PRELOAD:

"Preload a strcmp that returns 0 and the check passes."

The canonical example. In every tutorial. Exactly what you'd do — if the binary called strcmp.

It doesn't.

The comparison is inlined

It's a -O2 build; Lecture 6 already showed the licence logic inlined into its caller. The hook would load, run, and change nothing.

$ objdump -d auractl | grep strcmp # nothing $ readelf -r auractl | grep strcmp # not in the PLT

If the function you mean to hook doesn't appear as a PLT-crossing call, LD_PRELOAD can't reach it.

The generic answer omits the one fact that decides whether it applies — because it was produced without looking at this binary's PLT.

Falsification Drill. Falsifying observation from the room: "if it uses strcmp, there's a call strcmp@plt and strcmp is in the PLT." Check both. Record: textbook answer, not this binary.

The Lecture 4 pattern, again.

A recognisable question triggered a recognisable answer — and the recognition happened instead of the checking.

The check is thirty seconds of objdump.

Summary

  • An executable is a structured document assembled by the loader
  • ELF described twice: segments for the loader, sections for tools. The program needs only segments — so stripping doesn't stop it running
  • A relocation is a note to fill in an address later. Static = build time (big, self-contained); dynamic = load time (small, shared, dependent)
  • PLT/GOT enables lazy binding: library calls resolve on first use. The GOT slot visibly changes
  • Stripping removes your names, never the dynamic symbols, PLT/GOT, strings, or logic. Library calls map into stripped code
  • LD_PRELOAD interposes on dynamic calls; can't reach inlined, internal, static, or direct-syscall code
  • PE and ARM64 are the same concepts differently spelled
  • The tool's failure: "preload strcmp" for a binary that never calls it. Check the PLT
