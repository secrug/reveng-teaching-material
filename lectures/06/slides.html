A tool has existed for twenty years that turns assembly into readable C instantly. You've been reading it by hand instead.

Why?

Because a decompiler produces fluent, plausible, confident output — and it is sometimes wrong — and there is no way to tell which parts except by reading the assembly underneath.

Meet it first, and you learn to read its output.
Meet it sixth, and you learn to check it.

Disassembly is not a lookup

x86 instructions are 1 to 15 bytes. Start decoding at the wrong offset and you get a valid but entirely different instruction stream.

There is no marker in the bytes saying "an instruction begins here."

So first you must know where the instructions start.

Two strategies, two failures

Linear sweep

Decode start to end, one after another. Fast, complete.

Breaks on data inside .text — a jump table, an inlined constant. Decodes it as instructions, and because lengths vary, may never resynchronise.

Recursive descent

Follow control flow from entry points. Accurate about what is really code.

Lecture 3 gave you the problem: jmp rax. A computed target can't be known, so code beyond it is never reached, never disassembled.

Real tools combine both, add heuristics, and do very well.

Telling code from data in a stripped
binary is undecidable.

Not difficult. Provably impossible, by reduction to the halting problem.

Every disassembler you will ever use is making educated guesses. Ghidra guesses very well. It is still guessing.

Failure mode zero, underneath everything else today.

  • Structure — Lecture 3 in reverse. When the graph doesn't fit, you get gotos

Now look at that diagram again.

It is the Lecture 1 compilation pipeline run backwards.

And by Lecture 1, the information was destroyed.

Every backwards arrow is an inference. The decompiler cannot un-destroy anything. It produces the most likely source consistent with the machine code.

Most likely is not actual.

The six failure modes

  1. Wrong types — int for a pointer, unsigned for signed. Shows up as arithmetic that makes no sense
  2. Invented variables — uVar3, local_28. Some are real; some are artefacts of how it split registers
  3. Dropped side effects — a flag set, a global touched. Things that don't fit the C model get silently omitted
  4. Mis-structured / mis-bounded loops — Lecture 3's off-by-one, now automated
  5. Wrong calling convention — hand-written asm reads args from the wrong registers. Confident, wrong signature
  6. Missed indirect calls — call rax has no visible target. Whole regions look unreachable

This doesn't mean decompilers are bad. It means they are generators, and generators are things you verify.

Navigating: do not scroll

A binary has thousands of functions. Reading them in address order is the RE equivalent of reading a dictionary front to back.

A cross-reference records "this location is referred to from these other locations."

string "invalid licence" → xref → the function that prints it → xref → its two callers → one of them is the check

Under a minute, in a binary you've never seen, without reading anything irrelevant.

That's triage. Lecture 9 makes a method of it.

Renaming is not tidying up

When you work out that param_1 is a char *, tell the tool. Three things happen:

  • Output improves. Types propagate. *(int *)(param_1 + 0x18) becomes cfg->checksum — everywhere that pointer flows
  • You stop re-deriving. A named function is a conclusion you don't reach twice
  • Your reasoning becomes reviewable. The annotations are your hypothesis log — someone can see what you concluded and disagree

You supply the ground truth.
The tool does the bookkeeping.

You determined the struct layout by reading offsets. The tool applies it consistently across ten thousand lines — work you should never do by hand.

This is also exactly the relationship you want with any assistant.

Now a function


int check_license(char *key) {
    return 1;
}

The decompiler is correct. That function does return 1.

Cross-reference it.

It is called once — and the result is discarded

The actual validation is inlined into the caller: a rolling hash over the key bytes, compared against a value derived from the config.

check_license is a decoy.

The decompiler did not lie. It accurately reported a true property of the bytes.

Ask a model "how does licensing work here?" and it will read that function and describe it fluently and confidently — also reporting a true property of the bytes.

Both are wrong about the program, and neither is wrong about the code.

Scripted wrong turn: YOU start by reading check_license too. "OK so it just returns 1, that seems too easy—" then stop. "Wait, who even calls this?" Recover with the xref. Model catching your own pattern-match.

The missing thing is intent.

"This function is bait" is not a property of the bytes. It's a property of the whole program in the context of what someone was trying to achieve.

No amount of local analysis recovers it. It came from noticing the return value went nowhere — and asking why would anyone write a function whose result is ignored?

That question doesn't automate, because it isn't a question about code. It's a question about people.

The decompiler and the model are the same species of thing. Both consume a program and emit a likely interpretation. Both are fast, usually right, and confidently wrong exactly where the program departs from typical.

Run the generators to save time.
Check them against evidence.

The checking is possible only because you can read the evidence.

Which is what five lectures were for.

A tool that produces confident plausible output is dangerous to someone who cannot check it, and enormously powerful to someone who can.

Before you leave with the wrong conclusion

The honest counterweight

That decompiler just converted two hundred lines of assembly into readable C in about one second, correctly, for roughly 95% of the functions in this binary. By hand that's a day.

A model will rename forty variables sensibly, summarise a large unfamiliar codebase, recognise a standard algorithm from its constants, and write your tooling script — faster than anyone in this room.

These are not consolation prizes. Refusing to use them is not rigour. It's waste.

Mandatory, not optional. A room that concludes "AI bad, hand-reading good" has misunderstood as badly as one that concludes "AI solves everything." The lesson is calibration, not rejection.

The claim is narrow:

the last 5% is where
the answer usually hides.

The decoy, the custom constant, the misread signedness, the dropped padding — these are not evenly distributed.

They cluster exactly where someone was doing something interesting. Which is exactly where you are looking.

Use the tools for the 95%.
Be the person who handles the 5%.

Summary

  • Code vs data in a stripped binary is undecidable. Every disassembler guesses, well
  • Linear sweep desynchronises on embedded data; recursive descent misses everything behind an indirect jump
  • A decompiler is the compilation pipeline backwards — every arrow an inference over destroyed information
  • Six failure modes: types, invented variables, dropped side effects, loop structure, calling convention, indirect calls
  • Navigate by cross-reference. Start from a string or an import
  • Renaming records hypotheses, improves output, makes reasoning reviewable
  • Neither tool can represent intent. A decoy is a true fact about the bytes and a lie about the program
  • Decompiler and model are generators; the bytes are evidence
  • The tools are excellent for ~95%. The remaining 5% is where the answer is
